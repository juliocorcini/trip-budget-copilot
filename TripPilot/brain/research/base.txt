11. A regra matemática do nosso app
Eu manteria a matemática simples o suficiente para você entender e confiar nela.

Saldo operacional
saldoOperacional =
  orcamentoDaFase
  - reservaProtegida
  - gastosPessoaisRegistrados
  - despesasFuturasReservadas
Média diária disponível
mediaDiariaDisponivel =
  saldoOperacional / diasRestantesDaFase
Essa base segue a ideia usada pelo TravelSpend, mas subtrai explicitamente a reserva protegida e os compromissos futuros antes de calcular o valor livre. 

Saldo acumulado
saldoAcumulado =
  valorEsperadoAteHoje
  - gastosCotidianosAteHoje
Valor liberado para uma saída
reforcoPermitido =
  Math.max(0, saldoAcumulado) * 0.5

tetoSeguroDaSaida =
  metaDaSaida + reforcoPermitido
Por padrão, apenas metade do saldo acumulado melhora o teto de uma única saída.

Você pode alterar essa regra nas configurações, mas começar com 50% evita destruir toda a economia da semana em uma única noite.

4. Como calcular quantas vezes você ainda pode ir ao bar
O aplicativo começa pelo orçamento disponível da fase.

saldoLivre =
  orcamentoDaFase
  - reservaProtegida
  - despesasFixasPendentes
  - previsaoDeGastosEssenciais
Os gastos essenciais incluem aquilo que você provavelmente ainda precisará pagar:

previsaoDeGastosEssenciais =
  custoEsperadoDosDiasEmCasa
  + custoEsperadoDeMercados
  + transportesNecessarios
  + compromissosPlanejados
Depois disso, sobra uma verba flexível:

verbaFlexivel =
  saldoLivre
  - previsaoDeGastosEssenciais
Agora o aplicativo calcula:

quantidadeDeBaresPossiveis =
  Math.floor(verbaFlexivel / custoSeguroDeUmaNoiteDeBar)
Mas ele deve apresentar duas respostas distintas.

Indicador	Significado
Noites recomendadas	Quantas vezes você pode sair preservando mercado, passeio e margem
Máximo teórico	Quantas noites caberiam se você reduzisse outros gastos flexíveis
Exemplo:

Você pode ir ao bar mais 4 vezes com tranquilidade.
Seria possível ir 6 vezes, mas isso reduziria sua margem para restaurantes e passeios.

Isso é muito melhor do que apenas informar uma média diária.

5. Ficar em casa pode financiar uma saída, mas com uma pequena correção
Sua ideia está certa na prática:

Se eu ficar mais dias em casa gastando quase nada, ganho espaço para mais uma noite no bar.

Apenas existe um detalhe matemático.

Se o custo médio de um dia em casa for realmente €0, ficar em casa não cria dinheiro. O que acontece é que você deixa de consumir parte da verba flexível que poderia ter usado naquele dia.

O aplicativo pode traduzir isso de um jeito intuitivo:

Você economizou €24 em relação ao ritmo previsto
Isso equivale a 73% de uma noite comum no bar.

Depois de mais dois dias econômicos:

Você acumulou €36
Uma nova noite de bar foi liberada sem prejudicar o restante da fase.

Essa gamificação faz sentido porque mostra uma recompensa concreta sem inventar dinheiro.

Exemplo ilustrativo
Imagine que seu custo seguro por noite de bar seja €32.

Situação	Economia acumulada
Segunda em casa, gasto €0	+ €5
Terça em casa, gasto €2	+ €3
Quarta em casa, gasto €0	+ €5
Quinta em casa, gasto €0	+ €5
Sexta em casa, gasto €3	+ €2
Economia anterior	+ €12
Total acumulado	€32
O aplicativo diria:

Você liberou uma saída adicional
Seu saldo econômico acumulado já cobre uma noite média de bar.

12. PWA ou Kotlin?
Para seu caso, eu não começaria com Kotlin.

Eu faria uma aplicação web em React e TypeScript, instalável como PWA, mas prepararia o código para receber uma camada Android com Capacitor logo depois.

Comparação prática
Critério	PWA com React e TypeScript	Android nativo com Kotlin
Velocidade para criar com IA	Maior	
Facilidade para você revisar o código	Maior, porque seu dia a dia já é JavaScript	
Hospedagem gratuita	Sim	
Atualização imediata após publicar	Sim	
Instalação sem Play Store	Sim	
Uso offline	Sim	
Banco local	Sim	
Acesso pelo computador	Sim	
Uso no iPhone futuramente	Sim	
Notificações locais muito confiáveis	Limitado	
Recursos Android mais específicos	Limitado	
Trabalho inicial	Menor	
Uma PWA usa tecnologias web, pode compartilhar uma única base entre aparelhos, pode ser instalada e pode funcionar offline. IndexedDB serve para armazenar dados estruturados localmente no navegador. 

Onde a PWA fica limitada
O ponto delicado são os alertas quando o app está fechado.

A Notifications API consegue exibir notificações do sistema, inclusive por service worker, mas ainda não funciona da mesma forma em todos os navegadores. A Background Synchronization API também tem disponibilidade limitada. Já a Push API pode receber mensagens vindas de um servidor quando o aplicativo não está em primeiro plano, mas exige service worker e uma parte remota. 

Isso significa:

Situação	PWA resolve bem?
Registrar gasto rapidamente	Sim
Funcionar sem internet	Sim
Atualizar limites ao registrar bebida	Sim
Avisar imediatamente que você passou do teto	Sim
Exibir alerta com app aberto	Sim
Mandar lembrete exato após 45 minutos com app fechado	Não é garantido em todos os cenários
Criar uma notificação persistente durante a noite	Pode exigir camada nativa
13. A melhor escolha não é PWA ou Kotlin
A solução mais inteligente para você é:

React, TypeScript, PWA e uma camada Android opcional com Capacitor
Você começa rápido com uma aplicação web instalável.

Quando o fluxo principal estiver funcionando, adiciona Capacitor ao mesmo projeto e gera um APK Android. O Capacitor permite usar uma aplicação web em Android e iOS e oferece plugins nativos. 

Para o seu caso, o plugin mais interessante é o de notificações locais. Ele permite agendar notificações diretamente no aparelho, sem depender de um servidor enviando push. Também permite programar data, horário e repetição. 

Assim, quando você começar uma saída às 22h, o app pode agendar:

Horário	Notificação
22h45	Você registrou os gastos recentes?
23h30	Confira quanto ainda cabe na sua noite
00h15	Antes de pedir outra bebida, abra seu saldo
01h00	Vale continuar gastando ou já deu por hoje?
Quando encerrar a saída, o aplicativo cancela os alertas restantes.

Isso é mais confiável do que depender apenas da PWA e muito mais rápido do que construir tudo em Kotlin.

14. Quando Kotlin nativo faria sentido
Kotlin seria a melhor escolha caso você decidisse que o aplicativo será exclusivamente Android e que os recursos do sistema são o centro do produto.

Por exemplo:

Widgets mais completos na tela inicial.

Notificação persistente com botões de ação.

Alertas agendados com maior controle.

Tarefas em segundo plano.

Integrações específicas do Android.

Publicação como aplicativo Android completo desde o início.

No Android nativo, o WorkManager é recomendado para tarefas que precisam continuar funcionando mesmo se o aplicativo sair da tela, fechar ou se o aparelho reiniciar. Ele também permite trabalhos periódicos e reagendamento após reinicializações. 

Mas isso cobraria um preço: mais tempo de construção e menor facilidade para usar a mesma aplicação no computador ou no iPhone.

Para seu objetivo atual, seria usar uma bazuca para registrar um churro de €4.

A IA pode construir isso rapidamente, mas não deve receber apenas:

Isso produziria uma interface genérica e cálculos inconsistentes.

  01-product-goal.md
  02-user-scenarios.md
  03-budget-rules.md
  04-data-model.md
  05-screen-flows.md
  06-alert-rules.md
  07-offline-and-backup.md
  08-acceptance-tests.md
  09-out-of-scope.md
O arquivo mais importante: regras de orçamento
Ele deve definir claramente:

Média diária simples não controla limites.

Gastos são agrupados por sessão.

Mercado possui frequência e ticket médio próprios.

Bar possui média por sessão, não somente gastos de bebidas.

Reserva protegida nunca entra como dinheiro livre.

Compra pessoal não reduz a verba cotidiana de Burgos.

Saque apenas transfere dinheiro para a carteira física.

Gasto compartilhado afeta sua parcela real, não necessariamente o valor pago no cartão.

Um evento especial não altera automaticamente a média típica.

O aplicativo sempre mostra o impacto da próxima decisão.

Toda previsão informa o nível de confiança.

O usuário consegue entender de onde veio cada número.

Abaixo está a especificação completa para passar a uma IA de desenvolvimento. Ela já contém o conceito do produto, as regras matemáticas, a estrutura técnica, as telas, os testes e a ordem de implementação.

ESPECIFICAÇÃO PRINCIPAL DO PRODUTO
Nome provisório
Travel Budget Copilot

O nome é temporário. Não gastar tempo criando marca agora.

Idioma inicial
Português do Brasil.

Objetivo deste documento
Construir uma aplicação web instalável no celular para ajudar uma pessoa a controlar os gastos durante uma viagem.

O aplicativo não deve ser apenas um registrador de despesas.

Ele deve ajudar o usuário a tomar decisões antes e durante cada gasto.

A pergunta principal do produto é:

Quanto posso gastar agora sem prejudicar o restante da viagem?

A aplicação deve mostrar de forma simples:

Quanto dinheiro ainda está livre.

Quanto precisa continuar reservado.

Quantas saídas semelhantes ainda cabem no orçamento.

Quantos mercados ainda estão cobertos.

Como uma nova compra afeta os próximos dias.

Quando o usuário já deve parar de gastar em uma saída.

Quanto cada pessoa deve pagar quando uma despesa é compartilhada.

Quanto saiu da conta do usuário e qual foi o custo pessoal real dele.

1. CONTEXTO DO USUÁRIO
O primeiro usuário será Julio.

Ele está hospedado na casa da irmã em Burgos, na Espanha, durante parte da viagem de 2026.

Na maior parte dos dias úteis, ele trabalha remotamente em casa e gasta pouco ou nada.

Em alguns dias, ele:

Compra itens no mercado.

Divide despesas com familiares ou amigos.

Sai para restaurantes.

Vai para bares.

Faz passeios locais.

Compra roupas, cosméticos, presentes ou outros itens pessoais.

Usa dinheiro físico.

Faz transferências para quitar despesas compartilhadas.

O padrão de gastos não é linear.

Não faz sentido dividir o orçamento total pelo número de dias e usar o resultado como teto rígido diário.

Alguns dias custam €0.

Algumas compras de mercado custam €20 ou €30.

Uma noite em um bar pode custar €25, €35 ou €50.

Um passeio pode custar mais.

O aplicativo precisa entender essas diferenças.

2. PROBLEMA CENTRAL
Aplicativos financeiros comuns olham principalmente para o passado:

Você gastou €42 ontem.

Este produto precisa olhar para o presente e para o futuro:

Você já gastou €28 nesta saída. Mais uma bebida de €7 ainda cabe no teto seguro. Depois disso, pare.

Outro exemplo:

Você ainda tem verba para aproximadamente quatro noites comuns de bar, cinco mercados e um passeio local antes do fim desta fase da viagem.

Outro exemplo:

Esta compra de €38 ainda cabe no orçamento total, mas reduzirá suas noites de bar disponíveis de quatro para três.

O aplicativo precisa transformar números em decisões fáceis.

3. O QUE APRENDER COM O TRAVELSPEND
Usar como referência conceitual as boas ideias do TravelSpend:

Orçamento total de viagem.

Recalcular o valor restante conforme despesas são registradas.

Mostrar superávit ou déficit acumulado.

Permitir excluir despesas especiais da análise cotidiana.

Reservar despesas futuras.

Registrar quem pagou e para quem a despesa foi feita.

Simplificar pagamentos necessários para acertar contas.

Funcionar offline.

Exportar dados.

Não copiar interface, textos ou código.

Criar uma solução própria com foco maior na tomada de decisão em tempo real.

5. PRINCÍPIOS OBRIGATÓRIOS
5.1 Média diária simples não controla o produto
A média simples pode existir como indicador secundário.

Exemplo:

const simpleDailyAverage = remainingBudget / remainingDays;
Esse número não deve ser usado sozinho para limitar um mercado, uma saída ou um passeio.

A tela inicial não deve mostrar apenas:

Você pode gastar €13,20 hoje.

Ela deve mostrar algo contextual:

Permanecendo em casa hoje, sua meta é gastar entre €0 e €5.

Uma noite comum de bar pode custar até €35 com tranquilidade.

Você ainda tem verba para aproximadamente quatro noites semelhantes.

5.2 O orçamento deve ser explicado
Todo número exibido precisa ser rastreável.

O usuário deve conseguir tocar no valor e ver como ele foi calculado.

Nunca mostrar uma recomendação misteriosa.

5.3 O custo pessoal é diferente do dinheiro que saiu da conta
Exemplo:

Julio paga €60 de mercado para três pessoas.

O cartão dele recebe cobrança de €60.

Mas a parte pessoal dele é €20.

O orçamento pessoal deve diminuir apenas €20.

Os outros €40 ficam registrados como valor a receber.

5.4 Transferência não é necessariamente despesa
Uma transferência para Bruno pode ser:

Quitação de uma dívida.

Empréstimo.

Compra de euros.

Reembolso.

Despesa real.

O usuário deve escolher o tipo.

Quitação de dívida não cria uma nova despesa.

5.5 Saque não é despesa
Exemplo:

Julio saca €80.

Registrar:

Wise: menos €80
Carteira física: mais €80
Despesa real: €0
Quando Julio gastar €12 em dinheiro:

Carteira física: menos €12
Despesa real: €12
5.6 Compras pessoais precisam ficar isoladas
Roupas, perfumes, cosméticos, presentes e compras semelhantes não devem distorcer a leitura da rotina em Burgos.

Exemplo:

Uma compra de €90 na Zara reduz a caixa Compras Pessoais.

Ela não reduz a verba cotidiana de mercado, bar ou restaurante, a menos que o usuário escolha explicitamente retirar o valor de outra caixa.

5.7 Reserva protegida não é dinheiro livre
A reserva de segurança deve continuar visível, mas nunca aparecer como dinheiro disponível para uma saída casual.

5.8 O usuário precisa gastar sem culpa quando existe verba
O aplicativo não deve apenas alertar sobre excessos.

Também deve dizer claramente quando uma saída cabe no orçamento:

Pode pedir. Mesmo após essa compra, seus mercados continuam cobertos e você ainda terá verba para três noites semelhantes.

12. APRENDIZADO DO PERFIL
O aplicativo deve começar com estimativas manuais.

Depois, os gastos reais ganham influência.

Não usar inteligência artificial remota para isso na primeira versão.

Usar cálculos determinísticos e fáceis de testar.

12.1 Média ponderada inicial
function calculateWeightedAverage(
  initialEstimate: number,
  initialWeight: number,
  observedAmounts: number[]
): number {
  const observedSum = observedAmounts.reduce((sum, value) => sum + value, 0);

  return (
    initialEstimate * initialWeight + observedSum
  ) / (
    initialWeight + observedAmounts.length
  );
}
Exemplo:

Estimativa inicial de uma noite em bar: €30
Peso inicial: 2
Primeira noite real: €39

Nova média estimada:
(30 × 2 + 39) ÷ 3 = €33
12.2 Valor típico
Calcular:

Média ponderada.

Quantidade de sessões típicas.

Intervalo observado entre sessões.

Menor valor.

Maior valor típico.

Nível de confiança.

12.3 Valor seguro
Não usar somente a média.

Criar safeEstimatedAmount.

Regra inicial:

function calculateSafeEstimatedAmount(params: {
  weightedAverage: number;
  median: number;
  observedAmounts: number[];
  safetyMultiplier: number;
}): number {
  const { weightedAverage, median, observedAmounts, safetyMultiplier } = params;

  if (observedAmounts.length < 3) {
    return Math.max(weightedAverage, median) * safetyMultiplier;
  }

  const sorted = [...observedAmounts].sort((a, b) => a - b);
  const p75Index = Math.min(
    sorted.length - 1,
    Math.ceil(sorted.length * 0.75) - 1
  );
  const percentile75 = sorted[p75Index];

  return Math.max(weightedAverage, median, percentile75);
}
Arredondar valores monetários adequadamente.

O multiplicador inicial pode ser:

1.15
Permitir configuração por perfil.

Função inicial:

function calculateExpectedRemainingOccurrences(params: {
  remainingDays: number;
  expectedFrequencyDays?: number;
  plannedRemainingOccurrences?: number;
}): number {
  const {
    remainingDays,
    expectedFrequencyDays,
    plannedRemainingOccurrences
  } = params;

  if (plannedRemainingOccurrences !== undefined) {
    return plannedRemainingOccurrences;
  }

  if (!expectedFrequencyDays || expectedFrequencyDays <= 0) {
    return 0;
  }

  return Math.ceil(remainingDays / expectedFrequencyDays);
}
O usuário deve poder ajustar manualmente a quantidade restante.

function calculateTradeoffScore(input: TradeoffScoreInput): number {
  return (
    input.optionalOccurrencesRemoved * 10 +
    input.plannedOccurrencesRemoved * 40 +
    input.essentialOccurrencesRemoved * 1000 +
    Number(input.touchesManualFutureReserveFloor) * 5000 +

}
